# Bubble Arena｜游戏需求与技术实现文档

> 版本 V1.0 · 2026-09-22 · 适用：Agent 分步开发

> 文档说明：这是需求、技术方案与逐任务验收合并版本。游戏规则中的数值是原型默认值，须经试玩确认。

# 1. 文档说明与项目定位

项目名称：Bubble Arena（暂定）。文档版本：V1.0（初版需求基线）。目标：以小任务逐步交付可在 PC 浏览器运行的原创 3D 卡通第三人称房间制多人射击游戏。本文将“产品需求、技术实现、验收标准、Agent 任务计划”放在一份文档中，供开发与后续任务拆解使用。

项目参考同类卡通射击游戏的房间对战、击倒和救援玩法，不复制任何第三方角色、地图、贴图、声音、商标或受保护的具体表达。发布前核查所用模型、动画、字体和音频素材的许可证。

## 1.1 交付范围

| 维度 | 首版目标 |
| --- | --- |
| 平台 | Windows/macOS 桌面端主流浏览器；键盘+鼠标；移动端非首版目标。 |
| 对战 | 先 1v1 双人闭环，再 2v2，最后按性能和网络测试扩展到 4v4（最多 8 人）。 |
| 场景 | 1 张完整核心地图 + 后续 1～2 张扩展地图，共 2～3 张。 |
| 武器 | 步枪、霰弹枪、狙击枪、泡泡发射器共 4 种基础机制。 |
| 游戏流程 | 入口 → 大厅 → 房间 → 队伍/地图/武器选择 → 准备 → 对战 → 结算 → 返回房间。 |
| 内容制作 | 低模/卡通风格，初期占位几何体；正式阶段引入 GLB/GLTF 角色、武器、地图及动画。 |
| 音频 | 背景音乐、武器、角色、交互和空间音效；生成与下载过程人工确认、Agent 负责集成。 |

## 1.2 暂不纳入首版

- 商城、充值、赛季、排位、反作弊商业系统、语音聊天、好友社交、跨平台移动触控、复杂装备成长及 UGC 地图编辑器。
- 初期不建设独立账号和战绩数据库；先使用游客昵称与临时会话。需要持久战绩时再接入 NestJS + MySQL。
- 不以“AI 全自动完成所有美术”为交付前提；角色手感、动画衔接、平衡性和美术一致性均需人工试玩验收。
## 1.3 术语与角色

| 术语 | 含义 |
| --- | --- |
| 房间 | 对局开始前的组队和规则设置容器。 |
| 对局 | 一局运行中的服务端权威比赛实例。 |
| 本地预测 | 客户端为降低操作延迟，在收到服务端确认前先计算本地运动。 |
| 服务端权威 | 服务器判定玩家位置、弹药、命中、伤害、得分和结算。 |
| 白盒地图 | 使用简单几何体表达的可测玩法布局，无正式美术资源。 |
| Agent | Claude Code/Codex 等开发助手；仅执行当前明确的小任务。 |

# 2. 产品功能需求（PRD）

## 2.1 玩家旅程与状态流

```text
入口/昵称 → 大厅 → 创建或加入房间 → 选队/地图/武器 → 准备
→ 房主开始 → 资源加载 → 比赛倒计时 → 进行中
→ 击倒/救援/淘汰/复活 → 时间或比分条件达成 → 结算 → 返回原房间
```

## 2.2 大厅和房间

| ID | 要求 | 可验收结果 |
| --- | --- | --- |
| FR-L01 | 游客输入昵称进入大厅；昵称需要长度和非法字符校验。 | 刷新前可识别当前会话；非法昵称给出提示。 |
| FR-L02 | 显示可加入房间的名称、人数、地图、状态。 | 两客户端对列表变更的显示一致。 |
| FR-L03 | 创建/加入/退出房间；房间有最大人数和可选密码。 | 满员与错误密码不可加入；退出后席位释放。 |
| FR-L04 | 玩家可切换红/蓝队伍并显示成员、房主、准备状态。 | 队伍人数超限时禁止切换。 |
| FR-L05 | 房主可选地图及规则；玩家可选武器并准备。 | 设置变化同步到所有房间成员。 |
| FR-L06 | 满足人数与准备条件后开始对局；结算后返回原房间。 | 反复开局不重复创建玩家或残留旧比分。 |
| FR-L07 | 房主退出、成员断线按明确规则处理。 | 房主转移或解散；无幽灵成员和卡死对局。 |

## 2.3 角色与摄像机

| ID | 要求 | 可验收结果 |
| --- | --- | --- |
| FR-P01 | WASD 移动、跳跃、重力、碰撞、斜坡和小台阶。 | 不能穿墙、悬浮或无限连跳。 |
| FR-P02 | 鼠标控制第三人称镜头；俯仰角限制与墙体避障。 | 贴墙及转角时镜头不严重穿模。 |
| FR-P03 | 普通移动时面向移动方向；瞄准时面向镜头的水平瞄准方向。 | 瞄准时可前后移动及左右平移。 |
| FR-P04 | 控制器参数可配置（速度、加减速、跳跃、转向等）。 | 修改参数不需改写输入和物理算法。 |
| FR-P05 | 视觉模型、动画与物理胶囊体分离。 | 替换 GLB 模型不改变角色物理行为。 |

## 2.4 战斗与比赛规则

| ID | 要求 | 可验收结果 |
| --- | --- | --- |
| FR-C01 | 步枪可开火、换弹，受弹药与射速限制。 | 无弹药/换弹中不可有效开火。 |
| FR-C02 | 准星瞄准与枪口射击路线独立，考虑近墙遮挡。 | 枪口被墙遮挡时不可射中墙后目标。 |
| FR-C03 | 服务端权威判定命中、生命值、击倒、救援、淘汰和复活。 | 客户端伪造伤害或位置不能改变服务端结果。 |
| FR-C04 | 计时、队伍比分、对局状态与结算由服务端管理。 | 双方看到相同最终结算。 |
| FR-C05 | 扩展霰弹散射、狙击开镜、泡泡投射物。 | 每把武器具有独立可测的射击机制。 |

## 2.5 首版建议规则参数（均可配置，需试玩定稿）

| 参数 | 原型默认值 | 说明 |
| --- | --- | --- |
| 玩家生命值 | 100 | 原型值；武器伤害后续平衡。 |
| 步枪弹匣 | 30 发 | 初始占位数值。 |
| 步枪射速 | 每秒 8 发 | 由服务端校验，不信任客户端触发次数。 |
| 击倒可救援时间 | 20 秒 | 原型规则；允许倒地时间内被队友救起。 |
| 救援操作 | 靠近后长按交互键 3 秒 | 中断条件另行定义；1v1 时可先使用模拟队友测试。 |
| 对局时间 | 5 分钟 | 超时按队伍分数结算；平局规则可配置。 |
| 地图切换 | 仅房间阶段 | 进行中的比赛不可换图。 |

> 规则决议点：击倒者能否移动、补刀方式、救援时受击是否中断、复活保护时长、复活点选择、平局与断线判负规则，需要在阶段 4 前确定并写入 GAME_DESIGN.md。以上参数是原型占位，不是最终平衡承诺。

## 2.6 音视频与用户界面

- HUD 显示准星、生命值、当前/备用弹药、比分、倒计时、交互提示；UI 状态不驱动每帧物理更新。
- 音乐：大厅、等待、战斗、胜利/失败；音效：四种武器、换弹/空仓、脚步、起跳/落地、命中/击倒/救援/复活、按钮/倒计时。
- 主音量、BGM、SFX 独立可调；声音启动遵循浏览器用户交互策略；敌方枪声随空间位置和距离衰减。
- 游戏资源缺失时提供错误或占位回退，不应让整个大厅失去操作能力。
# 3. 技术方案与系统边界

## 3.1 技术选型

| 层 | 方案 | 职责 |
| --- | --- | --- |
| Web 客户端 | React + TypeScript + Vite | 页面、房间 UI、战斗 HUD、输入与游戏生命周期。 |
| 3D 渲染 | Three.js + React Three Fiber + Drei | 模型、材质、灯光、摄像机、特效和动画。 |
| 物理 | Rapier（客户端及 Node.js 服务端） | 胶囊体角色控制、地形碰撞、射线/投射物检测。 |
| 实时多人 | Colyseus | 对战 Room、成员管理、协议、权威模拟与状态同步。 |
| 状态管理 | Zustand（低频状态） | 大厅、设置、HUD 显示等；高频模拟使用独立 game-core。 |
| 音频 | Howler.js / Web Audio API | 音频预加载、混音、BGM、空间音效。 |
| 业务持久化 | NestJS + MySQL（后期） | 账号、用户资料、战绩；非原型的必备依赖。 |
| 美术 | Blender / GLB / 合法素材库 | 模型、贴图、骨骼和动画；Agent 可用 Python 批量处理。 |
| 音乐与音效 | Suno 等 + Audacity | 生成、试听、裁剪、响度匹配、授权确认。 |
| 工程 | pnpm workspace + Git + Vitest + Playwright | 模块化代码、自动测试、回归及变更管理。 |

## 3.2 Monorepo 目录规划

```text
bubble-arena/
  apps/
    web/               # React：大厅、房间、渲染、输入、HUD
    game-server/       # Colyseus + Rapier：权威对战逻辑
    api/               # NestJS：账号/战绩，按需启用
  packages/
    shared/            # 消息类型、资源 ID、配置 Schema
    game-core/         # 不依赖 React 的模拟和武器规则
  assets-source/       # Blender 源文件、音频工程（Git LFS）
  docs/
    GAME_DESIGN.md
    ARCHITECTURE.md
    DEVELOPMENT_PLAN.md
    TASKS/
  AGENTS.md
  pnpm-workspace.yaml
```

## 3.3 模块边界与数据流

1. 客户端：采集输入（按键、瞄准朝向、操作序号）→ 本地预测 → 渲染；不决定自身权威坐标或伤害。
1. Colyseus：验证玩家身份及输入频率 → 固定步长模拟角色与武器 → 判定伤害和规则 → 同步状态与事件。
1. 客户端：基于服务端快照校正本地玩家，针对其他玩家做插值，触发非权威动画与音效。
1. 大厅 Room 管理成员与规则，对战 Room 管理比赛；避免客户端自行设置比赛结果。
1. 基础版优先 Colyseus 完成房间管理；NestJS 和 MySQL 仅在真实账号/持久化需求出现后引入。
## 3.4 物理与角色控制实现

- 使用胶囊体碰撞器和运动学角色控制器。每物理帧：读取输入、构造期望位移、由 Rapier 计算允许位移、更新运动学刚体、记录接地及速度。
- 垂直速度、重力和跳跃由游戏逻辑明确管理；普通运动学刚体不会自动获得符合需求的重力/跳跃行为。
- 地图碰撞使用简化静态碰撞体；视觉 GLB 模型不直接承担所有物理碰撞。
- 固定物理步长是初始架构约束；渲染与网络广播可以使用不同频率。
- 摄像机使用独立的避障检测；瞄准点由摄像机获得，真正命中由枪口射线和服务端校验决定。
## 3.5 网络协议与服务端规则

```text
Input { seq, dtOrTick, moveX, moveY, jump, aimYaw, aimPitch, fire, reload }
Snapshot { tick, ackSeq, players: [...], matchState, scores }
Event { id, tick, type, actorId, targetId?, weaponId?, position? }
```

- 上面的对象仅表示协议设计意图，正式实现应通过共享类型和运行时校验定义合法范围；客户端不应传入伤害值、真实生命值或最终坐标。
- 服务器物理模拟初始采用 60Hz 固定步长作为测试参数；状态广播可以从约 10～20Hz 原型起步，随带宽、CPU 和手感实测调整，不将其作为无条件性能承诺。
- 客户端为自己做输入预测与权威校正，为其他玩家做状态插值；开火音效和枪口闪光可立即反馈，但有效伤害以服务器判定为准。
- 初期 Colyseus/WebSocket 满足小规模原型目标；高延迟及丢包条件下的射击手感需专门测试，不能把 WebSocket 等同于专业 UDP 射击协议。
- 必须设计房间满员、开始中的加入、断线、刷新、重连、房主退出和异常结算路径。
## 3.6 音频和素材接入

- 音效统一使用稳定资源 ID：weapon.rifle.fire / player.jump / ui.ready 等，资源与触发逻辑分离。
- 第一阶段用静音占位或可授权测试音；正式阶段生成并审核音乐、枪声、脚步、UI 等资源。
- 单次音效统一裁剪首尾静音并调整响度；BGM 需要人工检查循环点，提示词中的 seamless loop 不能替代实际试听。
- 多人音效不传输音频流：只同步开火、受击等必要事件，由各客户端根据声音位置自行播放。
- 外部音频/模型生成平台的使用与商用授权在最终导入前记录来源、生成账户/订阅状态及许可，不臆测所有输出都可商业发布。
# 4. 非功能性需求与质量门槛

| ID | 类别 | 验收原则 |
| --- | --- | --- |
| NFR-01 | 可运行性 | 每次任务通过 typecheck/build；核心行为提供可复现的手动或自动验证步骤。 |
| NFR-02 | 画面性能 | 以约定测试 PC 上 60 FPS 为优化目标；实际设备、分辨率与画质档位在性能阶段锁定。 |
| NFR-03 | 网络质量 | 至少在低/中/高延迟测试档中观察瞬移、命中不一致与断线行为，并记录结果。 |
| NFR-04 | 安全与信任 | 客户端不具备直接写入生命值、比分、他人坐标的权限；输入频率和消息长度受限。 |
| NFR-05 | 可维护性 | 物理与规则逻辑脱离 React；共享协议单处定义；每个任务对应 Git 提交。 |
| NFR-06 | 资源合规 | 第三方及 AI 素材需保留来源和许可记录；不直接复制参考游戏素材。 |
| NFR-07 | 回归测试 | 修复缺陷增加相应测试或复现脚本；不可只验证单一成功路径。 |

# 5. Agent 逐任务执行规则

## 5.1 单任务契约

1. 每次只领取一个任务 ID；Agent 先读取 AGENTS.md、对应任务卡与直接相关的代码文件。
1. 任务卡必须包含：唯一目标、前置条件、允许修改模块、明确不做事项、验收步骤和输出清单。
1. 若任务需要跨越多个独立系统，先拆成 2～4 个更小任务，禁止直接实现整个阶段。
1. 完成后运行针对性测试与构建；视觉交互由真人试玩，Agent 不得将“类型检查通过”等同于“手感良好”。
1. 报告修改文件、已验证结果、未完成事项；当前任务结束即停止，不自动做下个编号。
1. 经人工验收后 Git 提交或合并；出现回归先回退或修复当前任务，再继续。
## 5.2 可复制的任务卡模板

```text
任务 ID：<阶段.编号>
唯一目标：<用一句话说明>
前置条件：<已通过的任务 ID>
允许修改：<模块/文件范围>
本次不做：<明确排除的功能>
实现步骤：<最多 3～5 条>
验收：<可观察或可测试的结果>
交付：<改动文件、命令与结果、手动复现步骤、待办>
停止条件：当前任务完成后停止，不继续下一任务。
```

## 5.3 阶段验收与发布门槛

每个阶段最后留出“阶段验收”关口。只有阶段功能可重复操作、关键缺陷已修复、回归检查通过且 Git 有可回退提交，才进入下一阶段；不得因后续新需求回头在未验收代码上连续叠加功能。

# 6. 逐阶段细分开发任务（每行单独交付 Agent）

## 阶段 0｜工程初始化

阶段交付：可运行、可构建的最小 3D 项目；本阶段不做游戏玩法。

| 任务 ID / 目标 | 独立验收条件 |
| --- | --- |
| 0.1  初始化仓库和 pnpm workspace | 根目录、workspace、gitignore 和 README 存在，空构建正常。 |
| 0.2  创建 web/Vite/React/TS | pnpm dev 可打开页面，TypeScript 类型检查通过。 |
| 0.3  安装并验证 R3F | 仅显示 Canvas 和立方体，控制台无相关错误。 |
| 0.4  加入 Drei 与 Rapier 依赖 | 构建通过；暂无移动和碰撞逻辑。 |
| 0.5  划分目录与模块约束 | 创建 core/player/camera/weapons/maps/audio/network 空模块及索引，不预实现功能。 |
| 0.6  建立检查脚本 | typecheck、build、test、lint（按需）可单独运行。 |
| 0.7  建立 AGENTS 与任务模板 | 规定单任务边界、验收/报告格式及禁止越界事项。 |

> 阶段门槛：完成本阶段全部必要任务，复测上一阶段核心路径，通过 typecheck/build/相关测试，人工验收后才开启下阶段。

## 阶段 1｜3D 场景与基础物理

阶段交付：胶囊体能在白盒地图中移动、跳跃、落地并正确碰撞。

| 任务 ID / 目标 | 独立验收条件 |
| --- | --- |
| 1.1  创建基础场景 | 80×80 地面、基础灯光、静态摄像机、测试立方体正常显示。 |
| 1.2  创建 Rapier 物理世界 | 固定步长配置生效；仅引入 Physics，不加角色。 |
| 1.3  地面静态碰撞 | 下落测试物体被地面阻挡。 |
| 1.4  创建胶囊体玩家 | 玩家位置和胶囊碰撞器对应；不控制移动。 |

## 7.1 开发前必须确认的最小决策

- 原型默认移动速度、跳跃高度、摄像机距离及瞄准模式开关键；在阶段 2 试玩后锁定。
- 击倒/救援/淘汰/复活细则；在阶段 4 前写定状态转换和例外条件。
- 首版优先 1v1 或 2v2，以及初版比分规则；在阶段 4 前确定。
- 服务器测试环境、外网域名、是否需要账号持久化；在阶段 9 前确定即可。
